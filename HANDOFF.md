## 4. HOW IT WORKS

### 4.1 Server-driven UI

- A design is a set of screens; each screen is a tree of nodes {id, type, props, children}. It is stored as JSON in design_versions.document, with a theme (palette, style, overrides).
- The dashboard and the app render with the SAME registry and renderer (one file, two readers), so a design looks the same in the editor and on the phone.
- A published version is immutable (database trigger). A change is a new draft version that gets published. At most one version per design is published (unique index). Rollback is a status flip.

### 4.2 Which design a user sees: one database function

private.resolve_layout(user_id) decides; the first hit wins:

1. the user's own assignment (highest priority, inside its time window)
   2. the organization's assignment
   3. the organization's default published design
   4. the global fallback published design
   5. the app's built-in layout (app/assets/js/runtime/builtin.js)

It returns the layout, a trace that explains the choice (meant for the dashboard's Paths tab, which still computes it from local data; see 8.2 #1), the enabled features, screens removed because their feature is off, organization settings, and dataSources: the allowlist of tables and columns the layout may read. It is called only through public.resolve_my_layout() (the app) and public.resolve_layout_as_admin(user_id) (admins, for the Paths tab).

### 4.3 Data binding

- A screen declares its queries:
  ```json
  "sources": [{"id": "open", "from": "tasks", "where": [["status", "neq", "done"]],
               "order": "due_at.asc.nullslast", "limit": 25}]
  ```
- A component prop binds to the rows:
  ```json
  {"$bind": "query.open", "map": {"title": "title", "due": {"from": "due_at", "format": "date"},
   "state": {"from": "status", "values": {"done": "done", "todo": "open"}, "fallback": "open"}}}
  ```
- The Repeater component renders one component per row.
- The app refuses any table or column that is not in dataSources (from entity_configs), allows only a fixed set of operators, and caps limit at 200. Row-level security still decides which rows return.

### 4.4 Writes and offline

- Completing or reopening a task and pinning a note apply on screen at once, then PATCH through the REST API.
- If the server refuses (400, 401, 403, 404, 409, 422) the change is rolled back and explained. If the server is unreachable (offline, timeout, 5xx) the change stays and is queued in IndexedDB (the outbox), retried with backoff, kept across reloads, and repeated taps collapse into one write. Every request times out after 12 seconds.

### 4.5 Preview links

- A token is 32 random bytes, expires (24 hours by default, 30 days at most) and can be revoked.
- public.resolve_preview(token) is the ONLY database function the anonymous role may call; tests/verify.sql enforces that allowlist. A preview is read-only, shows a banner, records no telemetry and returns no records or secrets.

### 4.6 Accounts and roles

- Invite-only. Role and organization are read ONLY from the auth user's app_metadata, never from user_metadata (which the person signing up controls). A signup without an organization is refused with a readable message.
- Roles: super_admin, org_admin, designer, viewer, app_user. A user cannot change their own role, organization or status (trigger).
- Invited people get must_change_password = true; public.complete_password_change() clears it. The screen for it is not built yet.

### 4.7 Rules engine (inside the database)

- Triggers on tasks, notes, projects, jobs, customers and records queue rule_events, but only when an enabled rule listens for that event. The pg_cron job "rules-tick" runs private.rules_tick() every minute.
- Conditions: {all | any | not} of {left: "$record.field", op, right}. Actions: set_field, update_record, create_record, toggle_feature, notify_admin, call_webhook (https and public addresses only). send_email and send_push are recorded as "skipped": no provider is configured.
- Safety: failures are tracked per rule; 5 failures in a row disable the rule; rule-caused cascades stop at depth 3; a poison event backs off and is marked dead after 5 attempts. Admins can run it on demand with public.run_rules_now().

### 4.8 Telemetry

- path_events records screen views, actions and errors; batched, with a capped queue, flushed with fetch keepalive when the page is hidden. The dashboard's Paths tab is meant to show it; today it shows local demo data (8.2 #1).

```text

insert into public.design_versions (design_id, version_number, label, schema_version, document, theme, status)
select design_id, 4, 'My change', 1, document, theme, 'draft'
  from public.design_versions where id = 'f9727a96-683e-4a75-8e9b-4ac866159a1b'
returning id;

-- 2) preview it at .../app/?preview=<token>
insert into public.preview_tokens (token, design_version_id, organization_id, label, expires_at)
values (translate(encode(extensions.gen_random_bytes(32), 'base64'), '+/=', '-_'), 'NEW_ID',
        '11111111-1111-1111-1111-111111111111', 'review', now() + interval '24 hours')
returning token;

-- 3) publish: archive the current version FIRST (only one may be published)
begin;
update public.design_versions set status = 'archived' where id = 'f9727a96-683e-4a75-8e9b-4ac866159a1b';
update public.design_versions set status = 'published', published_at = now() where id = 'NEW_ID';
update public.design_assignments set design_version_id = 'NEW_ID' where id = '5b8961e1-c2f1-4a21-bcef-b1b220ec3f60';
commit;
```

Rollback: the same three updates with the two version ids swapped. Apps pick the change up on their next open (the cached layout revalidates in the background).

## 9. LESSONS LEARNED (do not repeat these)

- On Supabase, closing a function takes "revoke execute ... from public" AND "... from anon": Postgres grants to PUBLIC, and Supabase also grants to anon and authenticated by name.
- user_metadata is attacker-controlled: never read a role or an organization from it.
- app_users.id references auth.users: create the auth user first (invite); a trigger builds the app_users row.
- A theme from the database may be partial: always merge it over a complete default (app/assets/js/runtime/theme.js) or the renderer throws.
- Enum options in entity_configs must match the tables' CHECK constraints, and status words must match their CHECKs (rule_runs uses 'success', not 'succeeded').
- sendBeacon cannot send an Authorization header: use fetch with keepalive.
- A request without a timeout can hang forever; every request is bounded.
- Rule actions can trigger more rules; the depth cap stops loops.
- GitHub Pages: the workflow pushes the gh-pages branch, because the Actions token cannot create a Pages site through the API.
- Check what a design actually renders before publishing it (the first published version was skeletal and showed empty screens).
- Make sure a test's setup really triggers what it tests: the cascade check once set a task to the status it already had, so the rule never fired and the check failed for the wrong reason.
